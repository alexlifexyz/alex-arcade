# 街机路线图

本文记录街机现在到哪一步了、把全部游戏搬上掌机真正卡在哪里、剩下的活按什么顺序做。
它是一份规划文档：只给测量结果和设计，不替代 [`AGENTS.zh_CN.md`](../../AGENTS.zh_CN.md)
和验证门禁。

新增单个游戏的可重复流程见 [`new-game-guide.zh_CN.md`](new-game-guide.zh_CN.md)。

## 现在到哪一步

仓库里有 27 个 C 语言游戏模型、26 个浏览器机柜。27 个模型里，掌机上能摸到的是 17 个。

| 分组 | 数量 | 现状 | 缺什么 |
| --- | --- | --- | --- |
| 已在掌机 | 17 | 模型、渲染层、构建项、目录表和注册表都有 | 不缺 |
| 只有模型 | 10 | 模型和主机测试都有 | 缺 LVGL 渲染层 |

- **已在掌机（17）**：Striker、Tank 1990、Contra、Island、Runner、Cavalry、
  Pac Neon、Racer、Paws Sprint、Wave Walker、Fly Driver、Neon Pop、Fly Saber、
  Wind Rider、Pixel Flappy、Shy Fish、Devil Roulette——按菜单顺序列，也就是
  目录表的分类分组顺序。
- **只有模型（10）**：`pong`、`worldtime`、`sparkler`、`smash`、`bubble`、
  `huddle`、`splasher`、`laser_cat`、`bouncy`、`pawssprint_dx`。这些在浏览器街机
  里能玩，渲染层是 JavaScript 写的。

27 个模型加模板全部通过主机测试，所以差距完全在渲染层和菜单上，不在游戏正确性上。

## 27 款上掌机，真正卡在哪里

**不是卡在 Flash。** 把所有 `*_logic.c` 用 `-Os` 在主机上编译，27 个模型的代码加
数据合计约 271 KiB，最大的单个模型约 17 KiB。现有 17 个渲染层约 11.5k 行，缺的 10 个
大约再加 6k 行，也就是说整个 27 款的应用层大约在半兆这个量级，而应用分区有 3 MiB。
这些是主机侧的等比估算，不是固件实测；权威数字是 `tools/verify_firmware.py` 现在
每次构建都会打印的预算行：

```text
Protected firmware layout: PASS (App budget: N / 3145728 bytes (X% used, Y KiB free))
```

在断言「还有/没有空间」之前，先看这一行。

**第一个真正的拦路虎是菜单，现在已经拆掉了。** `main/main.c` 以前把每一项都画成
固定卡片，并随项数变多而压缩卡片高度；11 项时卡片已经只有 19 px 高，屏幕总高
320 px。现在它是固定 8 行的滚动窗口、卡片 24 px 高，卡片高度不再取决于有多少款游戏，
列表对任何数量都成立。

**剩下的拦路虎是 10 个缺失的渲染层。** 每个都是 400 到 900 行左右的独立工作，彼此
没有依赖。

**真要省空间，还有一块储备。** `demo_display.c`、`demo_button.c`、`demo_audio.c`、
`demo_battery.c`、`demo_wifi.c`、`demo_ble.c`、`demo_low_power.c` 都被编进了固件，
但菜单表里摸不到它们；而 `demo_ble.c` 是 NimBLE 主机被链接进来的唯一原因。把这些
摸不到的页面连同 `bt` 一起去掉，能腾出预算里可观的一块。Wi-Fi 必须留着：
`demo_battlecity.c` 用 ESP-NOW 做双机联机。在预算行真的显示空间不够之前不要动它，
动的时候要把改动前后的数字记下来。

## 设计：把游戏表拆成两张（已落地）

菜单表以前是 `main/main.c` 里的一个字面量数组，这让 `main.c` 成了「注册游戏的地方」，
而且没有任何办法把固件的游戏列表和浏览器的游戏列表对一遍。

现在已经拆开：

```text
main/game_catalog.c / .h    纯数据：id、显示名、分类、标志位
main/game_registry.c / .h   函数指针：每个 id 的 enter / exit / key
```

目录表里不含任何 ESP-IDF 或 LVGL 类型，所以
[`tests/test_game_catalog.c`](../../tests/test_game_catalog.c) 能把它编起来，断言
id 不重复且只用小写字母数字、名字不重复且不超过 `GAME_NAME_MAX_CHARS`、分类合法、
整张表按分类分组、跳分类一定落在某个分类的第一项并且一圈能回到出发点。注册表仍然
只属于固件，是接新页面的唯一入口，`game_registry_validate()` 在开机时会把目录表与
注册表的错位全部打到日志里。`main.c` 回归到只管菜单行为。

这套设计里有一条断言**还没有**落地：每个目录 id 在
[`simulator/catalog.js`](../../simulator/catalog.js) 里也存在。`pacman` 没有浏览器
机柜，今天这条就会红；而且 C 主机测试本来也解析不了 JavaScript。给 `pacman` 补一个
浏览器机柜，再写一个同时读两张表的 Python 门禁检查，这件事归到 P2。

## 设计：一个装得下 27 项以上的菜单

三个按键里本来就还有一个空着的手势。在游戏里长按 OK 是返回菜单；而在菜单里长按 OK
以前什么也不做。

- **滚动窗口（已落地）。** 8 行 24 px 卡片，占 `y` 52 到 272；选中项保持在窗口内，
  碰到边缘时窗口跟着滚，两端循环；标题牌右边有 `12/17` 位置牌，草地上写着选中项的
  分类。吉祥物挪到 `y` 280，站在列表下面而不是压在列表上。
- **长按 OK 跳分类（已落地）。** 浏览器目录定义好的六个分类，选中项跳到下一个分类的
  第一项。游戏里长按 OK 仍然是返回菜单，两个语义不冲突：两边不会同时在。
- **记住上次选的那个。** `0x9000` 处的 `nvs` 分区可用，且不在受保护布局里。存下
  上次选中的 id，之后再存每个游戏的最高分，掌机就从一张列表变得像一台游戏机。
  设备上的最高分，是最可能让小朋友玩第二次的那一个功能。

## 分期

每一期都能独立交付，并且以门禁全绿收尾。

| 期 | 做什么 | 结果 | 验证方式 |
| --- | --- | --- | --- |
| P0 | 修好门禁、主机测试自动发现、应用体积预算行、带测试的游戏模板、本套文档 | 打地基 | `./tools/validate.sh --static` |
| P1 | 滚动菜单、目录/注册表拆分、接上 6 款已就绪游戏 | 掌机上 17 款 | 固件构建加预算行，再过一遍真机 |
| P2 | 10 个缺失渲染层，每批两三个，从最简单的开始（`pong`、`worldtime`、`sparkler`，然后 `smash`、`bubble`、`huddle`、`splasher`、`laser_cat`、`bouncy`、`pawssprint_dx`） | 掌机上 27 款 | 每批：主机测试、固件构建、真机过一遍 |
| P3 | NVS 记住上次玩的、每个游戏的最高分、分类跳转 | 游戏机手感 | 存储模型跑主机测试，掉电保持靠真机验证 |
| P4 | 菜单顶部固定一个「我的游戏」位，放当前的模板副本，让小朋友手上的半成品永远只差一次短按 | 共创闭环 | 真机过一遍 |
| P5 | 只有预算行逼到这一步才做：去掉摸不到的参考页面和 NimBLE，并记录前后体积 | 腾空间 | 改动前后的预算行 |

P0 和 P1 已经落地，下一步是 P2。

## 这份路线图不放松的规矩

- 受保护的 Flash 布局、3 MiB 应用上限、`0x356000` 的 `cardid` 一个字都不动。
- 构建成功永远不当作硬件验证。构建、主机测试、设备测试分开报告。
- 每个游戏都保持模型层与渲染层分离、都保留主机测试，和小朋友一起做的也一样。
